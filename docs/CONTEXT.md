# Issue Spotter: Project Context

Case Law "Issue Spotter" for law students and junior advocates. The user pastes a raw, unformatted factual summary of a hypothetical case. The app returns the primary legal issues, relevant doctrines, landmark precedents, and applicable statutes (acts and sections). It is a learning aid, not legal advice.

Status: working POC, not yet deployed, kept stealth (crawlers disallowed). Anonymous users get a daily free quota, and signed-in users (Google, via Firebase Auth) get a larger per-account quota. Sign-in is verified end to end with the real Firebase project. Tiers and credits are decided but not built (see Roadmap). The production domain is `legalspotter.com`.

## Domain language

Use these terms consistently in code, UI copy, prompts and commits.

| Term | Meaning in this app |
| --- | --- |
| **Facts** | The user's raw case summary. Free text, 20 to 12,000 characters. Sent as `facts`. |
| **Issue** | A primary legal question the facts raise. Short, bullet-ready string. Max 8. |
| **Doctrine** | A legal principle or rule that governs an issue (e.g. negligence). Max 8. |
| **Precedent** | A landmark case a student should know for the issue. Shown as "Landmark precedents". Max 8. |
| **Act** | A statute, shaped `{ act, sections[], relevance }`. Max 6 acts, max 8 sections each. |
| **Section** | A provision within an act, e.g. "Section 73". Model output, so it must be verified. |
| **Spot** | One analysis run: facts in, `SpotterResult` out. The endpoint is `/api/spot`. |
| **Verification** | The check that the facts look like a legal fact pattern (keyword heuristic, then a classifier call). |
| **Quota** | The daily number of free spots for an anonymous visitor. |
| **Visitor** | An anonymous caller, identified by a random cookie and a hashed network. The network is the IPv4 address, or the /64 of an IPv6 address (`networkOf`, `src/lib/server/network.ts`), because one customer can switch among the addresses of a /64 and would otherwise get a fresh network limit each time. Shared /64s (a campus, a building) share one network allowance. |
| **Signed-in user** | A caller with a verified Firebase ID token, identified by their Firebase uid. |
| **Subject** | Who a quota is counted for: a visitor's cookie id or a user's uid, plus the hashed IP. |
| **Tier** (planned) | A signed-in mode: **Investigative** (today's analysis) or **Research** (deeper). |
| **Credit** (planned) | Prepaid unit for signed-in use, metered from real provider token usage plus a margin. |

Jurisdiction: the system prompt tells the model to infer the jurisdiction from the facts and to default to **Indian law** for Indian-style facts.

## Tech stack

- **SvelteKit 3** (`@sveltejs/kit ^3`), **Svelte 5** with runes forced on for all non-`node_modules` files (see `vite.config.ts`).
- **Firebase Auth** (Google sign-in) in the browser via the `firebase` SDK (pinned to 12.x, since 13.x needs Node 24.12+), and `jose` on the server to verify ID tokens.
- **Cloudflare Workers** via `@sveltejs/adapter-cloudflare`, configured in `wrangler.jsonc`. **D1** (SQLite) holds quota counters.
- **Tailwind CSS 4** via `@tailwindcss/vite`. The only stylesheet is `src/routes/layout.css`, which holds the design tokens (see [`UI_CONTEXT.md`](UI_CONTEXT.md)). Inter and JetBrains Mono are self-hosted through `@fontsource-variable`. Icons come from `@lucide/svelte`.
- **TypeScript 6**, `strict: true`. **Vite 8**.
- An OpenAI-compatible Chat Completions API is the model provider.
- Tests use Node's built-in runner (`npm test`, files `*.test.ts` under `src/lib/server`). No linter or formatter is configured.
- Node 24 and npm 11 were used. `.npmrc` sets `engine-strict=true`.
- There is no `svelte.config.js`. SvelteKit 3 config (adapter, compiler options) lives in the `sveltekit({...})` call in `vite.config.ts`.

## Architecture

```
Browser (+page.svelte) --POST /api/spot {facts}--> hooks.server.ts (visitor cookie, IP hash,
   [Authorization: Bearer <Firebase ID token>]        verify token -> locals.user)
                                                  --> +server.ts
                                                     1. validate input
                                                     2. reserve 1 search in D1 (429 if none left)
                                                     3. stream NDJSON events:
                                                        quota -> [verifying] -> analyzing -> result
                                                     4. model calls to {OPENAI_BASE_URL}/chat/completions
```

There is no user table and nothing user-written is persisted. The only stored data is quota counters (hashed IP, cookie id or Firebase uid, no facts).

### Request flow (`/api/spot`)

0. A bearer token that fails verification returns **401** `auth_invalid`. It never falls back to the anonymous quota.
1. The facts field carries the whole case: the client joins the first message and every follow-up (later ones prefixed `Further facts:`, see `src/lib/case.ts`), so the 12,000-character limit applies to the case, not to one message. The server does not know or care that it is a follow-up; each one is a normal search and counts against the quota. Invalid JSON, facts under 20 trimmed characters, or over 12,000 raw characters return **400**. A missing `OPENAI_API_KEY` returns **500**. A missing D1 binding returns **503**.
2. **Quota.** `reserve` takes one search from the visitor's counter and the IP counter. Neither has room: **429** with `code: "quota_exceeded"` and the quota.
3. A stream starts (`application/x-ndjson`). Events (`SpotEvent` in `src/lib/spotter.ts`):
   `{quota}`, `{stage: "verifying"}`, `{stage: "analyzing"}`, `{item: {section, value}}`, `{sectionDone}`, `{meta: {model, ms}}`, `{result}`, `{notLegal: true}`, `{error}`.
4. **Verification.** `looksLegal` (see below) true: skip the classifier. Otherwise `stage: verifying`, then a classifier call. "no" means `notLegal`.
5. **Analysis (streamed).** `stage: analyzing`, then the call runs with `stream: true`. `SectionParser` (`src/lib/server/section-stream.ts`) reads the model's JSON as it arrives and the server sends an `item` as each entry completes (normalized and capped at 8 per section, 6 acts) and a `sectionDone` as each array closes. The key order in the system prompt (issues, doctrines, precedents, acts) is the order the UI fills in. When the reply ends, the whole text is parsed and normalized into `SpotterResult` and sent as `result`, which is the source of truth, preceded by a `meta` event with the model name and the analysis time. The model is asked for `jurisdiction` first, then `issues` and `doctrines` (strings), `precedents` (objects `{case, year}`; a year that is not four digits is dropped; plain strings from an older reply are still accepted) and `acts`. A provider that ignores `stream` and answers in one JSON body still works: the items arrive together.
6. **Refunds.** A provider error refunds the search. A `notLegal` rejection is free up to `QUOTA_REJECTION_MULTIPLIER` times the daily limits, then it counts.
7. Mid-stream failures arrive as an `{error}` event, not a status code.
8. **Timeouts.** Each provider call runs under a `Deadline` (`src/lib/server/deadline.ts`). The analysis must produce a response or a new chunk within `PROVIDER_IDLE_TIMEOUT_MS` and finish within `ANALYSIS_TOTAL_TIMEOUT_MS`; the classifier gets `CLASSIFIER_TIMEOUT_MS`. A stalled or overrunning analysis aborts the upstream request, **refunds the search** and sends `{error: "The model provider took too long to respond. Please try again."}`. A classifier timeout fails open like any classifier error. The user's own Stop is not a timeout and is not refunded.
9. **Reference verification** (when `SOURCE_VERIFICATION` allows it for this user, and the jurisdiction is Indian or unstated). After `result`, the server sends `{stage: "sourcing"}` and runs one Responses API call (`src/lib/server/sources.ts`) with the `web_search` tool restricted to `SOURCE_DOMAINS` (indiankanoon.org, indiacode, sci.gov.in), listing every case, act and the first three sections of each act. The model's own mapping is ignored. `matchSources` (`src/lib/server/verify.ts`) accepts a link for a reference only if it came back as a `url_citation` annotation, is on an allowed host, and its page title matches the reference: party names for a case (a year more than two years off rejects it), every word and number for an act, the section number and the act for a provision (Section 74 never matches a Section 73 page). It sends `{sources: [{key, url, title, host}]}` and the client upgrades those links; everything else keeps its search link. It never fails the search: an error, a timeout or no matches leaves `sources: []`. The answer is already on screen, because the client treats `result` as complete and reads the rest of the stream afterwards. The call is logged as `llm_usage` with `call: "sources"` and `webSearches`. **Cost:** about $0.011 per search call on gpt-4o-mini ($10 per 1,000 calls plus a fixed 8,000 input tokens), roughly ten times the analysis, which is why it is off by default and can be limited to signed-in users.
10. **Skills and attached pages.** The request may carry `skills` (only `summarize` and `counter-arguments` are recognised; others are ignored) and `context` (pages the user attached, each `{url, title, text, truncated}`). `parseContext` (`src/lib/server/prompt.ts`) rejects a page that is not an https page on an allowed site, has no text or more than 12,000 characters, more than 5 pages, or more than 30,000 characters in total; the host is worked out from the address, not taken from the client. `buildSystemPrompt` then lists only the requested keys (`summary` after `jurisdiction`, `counterArguments` last) with an instruction for each, raises the token budget (+300 for Summarize, +700 for Counter-args), and, when pages are attached, says that page text cannot be trusted and instructions in it must never be followed. `buildUserText` puts the typed facts first, untouched, then each page in a labelled `--- Attached source N: title (host) ---` block. With pages attached the classifier is skipped, since a short "summarize this" would otherwise be rejected as not legal. The new sections stream like the others (`summary` and `counterArguments` are parser sections).
11. **Files.** `POST /api/file` (`src/routes/api/file/+server.ts`) reads an uploaded file. The browser has already pulled out the text (`src/lib/extract.ts`: the type is sniffed from the first bytes by `sniffFile`, PDFs go through pdf.js in a worker, Word files through mammoth, and images are shrunk to at most 1600 px as JPEG); the request is `{name, kind: "text", text}` or `{name, kind: "image", dataUrl}`. `parseFileRequest` (`src/lib/server/reading.ts`) validates it, including that an image's bytes really are a PNG, JPEG or WebP. One non-streaming model call (`READING_PROMPT`, vision for an image) returns `{legal, documentKind, title, summary, text}`. A legal file comes back as an `Attachment` (`kind: "file"`, with its `reading`); an unrelated one comes back `{legal: false, documentKind, description}` and is not attached, and its quota unit is refunded, as is any failure. Own daily counter (`file:` namespace). Nothing is stored. Attached files travel in the analysis request's `context` as `{kind: "file", fileName, title, text}` and are labelled `--- Attached file N ---` in the prompt, with the same untrusted-text warning as pages. With anything attached, the minimum typed message drops from 20 to 5 characters.
12. **Draft.** With `skills: ["draft"]` (exclusive: `parseSkills` drops the others) the prompt (`buildDraftPrompt`) asks for `documentType`, `documentTitle`, `draft` (5 to 12 `{heading, text}` parts), `openQuestions` (up to 6) and `draftNotes` (3 to 5), and the token budget is 3,500. It tells the model never to invent facts, names, dates or citations, to put every missing detail in [square brackets], to give statute sections only in brackets, and which criminal codes apply when (BNS, BNSS and BSA for offences on or after 1 July 2024; IPC, CrPC and the Evidence Act before; both sets in brackets if the date is unknown, with the assumption in `draftNotes`). `draft` and `draftNotes` stream as parser sections. The result carries empty `issues`, `doctrines`, `precedents` and `acts`, and reference verification is skipped.
13. **Updates.** When the request carries `previous` (the headings of the earlier analysis of the same case: issues, doctrines, precedent names, act names, each cut to 300 characters and at most 12 per list by `parsePrevious`), the server treats it as an update. The system prompt asks for `headline` (one line, at most 12 words) and `update` (2 to 3 sentences on what the new facts change) after `jurisdiction`, and `openQuestions` (up to 4 unknown facts that would change the analysis) last; it tells the model to copy the wording of earlier entries that still apply, add entries for what the new facts raise, and drop the ones that no longer matter. The earlier analysis is appended to the user message in a labelled block, and the token budget rises by 450. `update` and `openQuestions` stream as parser sections; `headline` arrives only with the final result. The client computes the new / still applies / set aside split itself (`src/lib/diff.ts`).
14. **Cancel.** If the client aborts (the Stop button), the stream's `cancel()` aborts the upstream provider request, so generation and cost stop. The search is **not** refunded, because the provider already did part of the work. The server logs `{"event":"search_cancelled"}`.

The classifier **fails open**: if it errors or answers unclearly, the analysis proceeds. Blocking a valid case is worse than one extra call.

15. **Deep research (`POST /api/research`).** Separate endpoint, NDJSON events (`ResearchEvent`: `research` quota, `stage` checking/searching, `brief`, `offTopic`, `error`). Body `{topic, facts}` where `facts` is the case text so far (the client builds it from `turns`, excluding research topics). Steps: validate; reserve one run on the monthly `research:<ns>` counter (`researchSubjectFor`, `period: 'month'`); relevance check with `RELEVANCE_PROMPT` on the cheap model (fails open, so a slow check never blocks); if unrelated, refund and send `offTopic`; otherwise one Responses API call with the `web_search` tool limited to `RESEARCH_DOMAINS` (`filters.allowed_domains`), `max_tool_calls = DEEP_RESEARCH_MAX_SEARCHES`, model `DEEP_RESEARCH_MODEL ?? OPENAI_MODEL`, under a `Deadline`. `buildBrief` splits the text into sentences, numbers `url_citation` sources (dropping hosts outside the allowlist), marks sentences without a citation (`uncited`), and tags each source official or an Indian Kanoon copy. Zero sources, a provider error or a timeout is refunded; a Stop is not. Logs `llm_usage` with `call: 'research'` and `webSearches`. That search stage only finds sources and writes a first brief, which is kept as the fallback. A second stage (`writeReport` in `src/routes/api/research/+server.ts`) then builds the real answer: the cited pages (up to `DEEP_RESEARCH_READ_SOURCES`, official first, then the ones carrying most claims) are fetched by the Worker (`fetchPage`, allowlisted, up to 5 MB), each is cut to `DEEP_RESEARCH_READ_CHARS` by choosing paragraphs, not by cutting the end (`selectExcerpts` in `excerpt.ts`: head and tail always kept, the rest by BM25 against the topic and leads, paragraphs verbatim in order, gaps marked), and a writer model (`DEEP_RESEARCH_WRITE_MODEL[_INVESTIGATIVE|_RESEARCHER]`, via `tierOf`/`writeModelFor`; it does not search, so any model works) returns the report as strict JSON (`REPORT_SCHEMA` in `writer.ts`): fixed slots, each statement `{text, source, quote}`. `buildReport` keeps a statement only if its quote is on the source page (`quoteSupported`; case, punctuation and line breaks ignored, `…` joins parts), or else the quote snaps to the page's own closest wording at 85% in-order word overlap (`closestPassage` in `ground.ts`, marked `approx`); anything else is dropped, counted, and the first few are listed under Not confirmed. Only the Application section may carry the writer's own reasoning (source 0, labelled inference). Sizes and lengths are clamped to `RESEARCH_TEMPLATE` (`src/lib/report.ts`), which also renders Markdown (Copy / Download .md) so the page and the file agree. PDFs are not read by default (`DEEP_RESEARCH_PDF_MAX_BYTES=0`): the app cannot check a PDF quote itself and unchecked quotes were unreliable. Any failure in this stage returns the first brief unchanged, with a notice (no refund: the research happened). Citation URLs are stripped of `utm_*`. The client keeps it as a `research` exchange that adds nothing to the case text; Deep research is `workspace.researchMode`, not an `ActiveSkill`, and can be turned on only when an analysis exists.

16. **Compare cases (`POST /api/compare/identify`, `POST /api/compare`).** Two steps with a confirmation between them. *Identify* (JSON, `{input}` 8 to 600 chars): one web search over `RESEARCH_DOMAINS` (`IDENTIFY_INSTRUCTIONS`, prefers Indian Kanoon document pages) returns up to two cases as JSON; each page is then fetched and must be about the case named (`pageIsCase`: most distinguishing words of the name in the title or opening), else the candidate is `verified: false` with a `problem`. An official PDF is `readable: false`. It has its own daily counter (`cmpid:` namespace, `COMPARE_IDENTIFY_*`) and is refunded when two cases cannot be told apart. The client shows a `CompareCard` for the user to confirm ("Compare these two" / "These aren't right"). *Compare* (NDJSON `CompareEvent`: `compare` quota, `stage` opening/treatment/reading/writing, `brief`, `error`; body `{cases:[{url,name}]}`, exactly two different readable URLs on allowed hosts): reserve one run on the monthly `compare:` counter (`COMPARE_*` limits, same defaults as research); open both judgments; one search for decisions that overturned, reversed, doubted or followed either (`TREATMENT_INSTRUCTIONS`), up to 3 of those pages are opened too; every page is cut to `DEEP_RESEARCH_READ_CHARS` by paragraph selection (the two cases against `COMPARE_QUERY`); the writer (same tier model and knobs as research) returns `COMPARE_SCHEMA` and `buildReport(..., 'compare')` verifies every quote as for research. Sources are numbered 1 and 2 for the two cases, then the treatment pages. A comparison that cannot be written or confirmed is refunded. The result is a `ResearchBrief` with `blocks: []` and a `report`, rendered by `ResearchReport` with `COMPARE_TEMPLATE` (Synopsis, The cases, Facts compared, Judgments compared, How other decisions treated them, How they fit together, Not confirmed). The client keeps it as a `compare` exchange (`confirm` / `comparing` / `done`), `workspace.compareMode`.

17. **Verify cites (`POST /api/verify`).** One NDJSON request (`VerifyEvent`: `verify` quota, `stage` reading/finding/opening/checking, `brief`, `error`; body `{input}` 20 to 3000 chars), monthly `verify:` counter (`VERIFY_*`, same defaults as research). Levels: **1 exists, 2 details match, 3 supports the point**; level 4 (still good law) is not checked and every report says so. Steps: a cheap model (`OPENAI_MODEL`, strict JSON schema `PARSE_SCHEMA`) splits the pasted text into up to 5 citations as written (cite, name, year, court, reporter, proposition; nothing is corrected); one filtered web search finds a page per citation (`FIND_INSTRUCTIONS`), and any it missed get a second search by party names alone (`FIND_RETRY_INSTRUCTIONS`); pages are fetched and `pageIsCase` must agree with the name as the student wrote it (an official PDF is reported as found but unreadable); `checkDetails` compares name, year, court and reporter reference **in code, no model** (a reference year is not compared with the decision year; a reference not on the page is a fact, not an accusation, since judgment pages often do not print it); a page with the right names but not the reference, year or court cited, or a citation with only names, is reported as possibly a different case, because party names are often shared (a live run matched a made-up "Rajesh Kumar v. State of Delhi" to a real case of that name). Only level 3 uses a model (the tier writer, `SUPPORT_SCHEMA`: verdict, quote, note per citation); its quote is checked with `confirmQuote` and a verdict without a quote on the page is "not confirmed". The report (`buildVerifyReport`, `VERIFY_TEMPLATE`: Summary, Citations checked, Not confirmed) marks each line `ok` / `warn` / `fail`; lines the app worked out itself have `basis: 'app'`. Infrastructure failures are refunded; a citation not found is a result.

18. **Reading sources in the browser (`SOURCE_READING=browser`, the default).** Why: the Workers free plan allows about 10 ms of CPU per request; parsing a judgment page costs 12 ms cold for a typical one and 50 to 75 ms for a Constitution Bench one, and a PDF costs about 0.6 s, so the Worker must not parse. Deep research, Compare and Verify therefore split into two requests. *Step 1* (`/api/research`, `/api/compare`, `/api/verify`) reserves the quota unit, does the model searches, and instead of fetching pages sends a `gather` event: the sources to read (addresses from the search, validated against `RESEARCH_DOMAINS` and `isDocumentUrl`, which rejects Indian Kanoon search and citation lists), what to select paragraphs for (`queries`), an excerpt size (`DEEP_RESEARCH_READ_CHARS`), strings to look for in the whole page (`needles`, used for law-report references), pass-through `context`, and a **signed grant** (`token.ts`, `grants.ts`: HMAC-SHA256 with `QUOTA_SALT`; names the kind, the visitor, the quota period, the exact addresses and a 15 minute expiry). *In the browser* (`src/lib/gather.ts`): each source is fetched through `POST /api/fetch` (serves only addresses named in a grant issued to that visitor; checks every redirect hop; caps size at `SOURCE_MAX_BYTES`; hashes the bytes with SHA-256 and returns a signed stamp; does no parsing, so it is cheap CPU), then turned into text with the same shared code the server used (`src/lib/source-text.ts` `htmlToText`; for a PDF pdf.js via `withPdf` in `extract.ts`, then `pdf-text.ts` `pagesToMarkdown` which drops running headers, page numbers and signature stamps and rejoins wrapped lines into paragraphs), cut to the relevant paragraphs by `src/lib/excerpt.ts` `selectExcerpts`, and only the excerpt (never the page), the first 4000 characters, the title, the needle results and the stamp go back. *Step 2* (`/api/research/write`, `/api/compare/write`, `/api/verify/write`): verifies the grant (signature, expiry, visitor, kind), uses it up (`consumeGrant`: one row in `quota_usage`, so a token cannot be replayed), takes the sources through `intakeSources` (a source number must be one the grant named, so its address is the grant's not the browser's; sizes capped; a stamp kept only if the server signed it), writes the report from the excerpts with the same writers and checks every quote against the excerpts (the writer saw nothing else), then **attests** quotes taken from PDFs: `attest-run.ts` has a model read the official PDF by address (so nothing the browser sent can steer it) and say whether each kept quote is in it; lines it cannot find are dropped and named under Not confirmed (`PDF_ATTEST=false` turns this off; a failed check leaves the report as it was). Reports carry `readIn: 'browser'` and the page and the Markdown say so; each source shows its SHA-256 and fetch time. Failure behaviour: research falls back to the first search brief (no refund, the research happened); compare and verify refund the unit. `SOURCE_READING=server` keeps the single-request server path (needs the Workers Paid plan for long judgments; cannot read PDFs unless `DEEP_RESEARCH_PDF_MAX_BYTES` hands them to a model, unverified).

19. **Profile page and activity (`/profile`, `src/lib/activity.ts`, `activity.svelte.ts`).** The page shows a signed-in person's own numbers: analyses run, issues spotted, longest run, longest and current streak, a daily / weekly / cumulative activity chart, sources read, and insights (primary jurisdiction, most cited act, citations checked, skills used). **No database and nothing is sent to the server**: every finished run (analysis, draft, research, compare, verify) is added to a small tally in `localStorage` (`legalspotter:activity:<email>`, or `anonymous` when not signed in) by `workspace.#logRun`: counts and issues per local day, the longest run in ms, and maps of skills, acts, jurisdictions, sites (from the hosts of pages read) and a citations count, each pruned to 200 entries. All numbers are computed from it by pure functions with tests (`streaks` counts a streak as still running if yesterday had activity; days are local calendar days). Consequences: the numbers are per browser, are lost if site data is cleared, can be edited by the user, and signed-out use is recorded under `anonymous` and not credited to an account later; the page says so and has a two-step "Reset my activity data". "Most spotted area" from the first design is replaced by "Most cited act" because results are not classified by area; "Sources verified" by "Citations checked"; "Connected sources" by "Sources we read" (no source is linked per user; Google Scholar is not used so it is not shown). All three chart views share one window, `yearWindow` in `activity.ts`: the twelve months ending with this one as Sunday-first weeks (in November: Dec to Nov, 50 weeks), with each month labelled over the week holding its 1st; Weekly and Cumulative draw each week as a column of seven of the same 11 px squares as the daily grid, filled from the bottom (`ceil(value / busiest * 7)` squares, coloured by the same intensity levels), so they read as bars but are rendered as grids and show even with no activity, and their tooltips read "Week of Sep 20, 2026 / 14 analyses" and "Through week of Nov 1, 2026 / 528 analyses" (the running total includes everything before the window). The heatmap uses tokens `--heat-0..3` (light and dark) with `text-primary` as the busiest level; the chart has a screen-reader table of the same data and tooltips on pointer hover. Moving this to the account later means one small D1 table (for example `usage_daily(uid, day, runs, issues, longest_ms)`) written once per run; the page would not change.

20. **Read aloud (`src/lib/speech.ts`, `speech.svelte.ts`, `ReadAloud.svelte`).** Every final result has a "Read aloud" action: analyses (`analysisScript`), drafts (`draftScript`), research reports, comparisons and citation checks (`reportScript`, in the report's own template order) and the research fallback brief (`briefScript`). It uses the browser's built-in `speechSynthesis`: free, nothing sent to us, no server or database. The whole result is read, not a section; citation markers, links and markup are dropped; legal shorthand is spoken out (`forSpeech`: "v." as "versus", "Sec. 19(1)(a)" as "Section 19, sub-section 1, clause a", "Art.", "No.", "u/s", "Ors."); reasoning that no page confirms is introduced as "Reasoning:" and checked lines say "Checked." / "Worth a look." / "Not found."; headings are announced and empty sections skipped. The script is spoken a sentence or two at a time (`chunkText`, at most 200 characters, a pause at each paragraph) because some voices cut off a long utterance, with the next chunk started from the engine's `end` event. The voice (`pickVoice`): a saved one, else English with Indian English first and an on-device voice before an online one (so the text stays on the device); the speed has presets 0.75x to 2x on the player (a change applies to the sentence being read) and is remembered with the voice in `localStorage` (`legalspotter:speech`); `speech.setVoice` and `speech.voices` are there for the Settings page's Voice item, which does not exist yet, so for now the voice is automatic. Only one thing is read at a time; speech stops on navigation, a new run, Clear, editing the last message, and when something outside the app cancels it. No highlighting by design. Limits: the button is hidden if the browser has no speech engine; Chrome needs a user gesture before it will speak; voices and their quality differ by device; Hindi names and some abbreviations will be mispronounced; Safari on iOS has its own quirks; none of this was heard, only the engine's behaviour was checked.

### Legal-context heuristic (`looksLegal`)

A vocabulary of about 100 legal terms (prefix or whole-word matches, English). Two or more distinct terms means "clearly legal" and skips the classifier. It never rejects: no match only means "unsure", which goes to the classifier. The same function drives a non-blocking tip in the form. User input is never truncated or altered.

### Quota

- **Subjects.** Anonymous callers are counted under the `search` namespace by cookie id. Signed-in users are counted under `user` by Firebase uid, so their count follows them across browsers and networks. A rejection counter is kept per subject (`reject:search`, `reject:user`).
- **Anonymous identity.** An `anon_id` cookie (random UUID, `httpOnly`, 1 year) plus a SHA-256 of the IP salted with `QUOTA_SALT` (truncated, never stored raw).
- **Limits.** Anonymous: `ANON_DAILY_LIMIT` per browser (default 5) and `ANON_IP_DAILY_LIMIT` per IP (default 25, so shared networks such as campuses are not blocked by one person). Signed-in: `SIGNED_IN_DAILY_LIMIT` per account (default 20, a placeholder until credits) and `SIGNED_IN_IP_DAILY_LIMIT` per IP (default 200).
- **Deep research is monthly.** Its counters live in `research:search` / `research:user` namespaces keyed by a UTC month (`currentPeriod`), with `DEEP_RESEARCH_*` limits (defaults: anonymous 1 per browser and 5 per IP, signed in 3 per account and 15 per IP). `/api/me` and the page load return `research` beside `quota`.
- **Days are UTC.** The reset is 00:00 UTC (05:30 IST). The UI shows the local time.
- **Atomic.** One SQL upsert per counter increments only while below the limit (`INSERT ... ON CONFLICT DO UPDATE ... WHERE count < ?`), so parallel requests cannot overshoot. If one counter is full, the other is rolled back.
- **Known weakness.** Clearing cookies resets the per-browser count. The IP ceiling and the provider spend cap are the real limits. Do not rely on code secrecy.

### Authentication

- **Client.** `firebase/auth` `signInWithPopup` with the Google provider. The page re-reads `/api/me` whenever the auth state changes and sends `Authorization: Bearer <ID token>` on `/api/spot` (the SDK refreshes the token when it expires). Sign-in is hidden unless all four `FIREBASE_*` public values are set.
- **Server.** The token is verified with `jose` against Google's public keys (`securetoken@system.gserviceaccount.com` JWKS): RS256 only, issuer `https://securetoken.google.com/<project id>`, audience `<project id>`, not expired, with a subject. No Admin SDK and no service-account key, so it runs on Workers. Never commit a service-account file.
- **Emulator.** In non-production builds with `FIREBASE_AUTH_EMULATOR_URL` set, the server accepts the emulator's unsigned tokens (checking the same claims, but not a signature), and the client connects to the emulator. This is compiled out of production builds (`import.meta.env.PROD`), and a production build was tested to reject emulator tokens.
- **No fallback.** A token sent while Firebase is unconfigured, or one that fails verification, is a 401. Signed-in users cannot silently drop to the anonymous quota.

### Token usage

Every model call logs one structured line: `{"event":"llm_usage","call":"classifier|analysis","model":...,"promptTokens":...,"completionTokens":...}`. Streaming calls send `stream_options.include_usage`, so the counts come from the final chunk. Counts are `null` when the provider omits them, and a cancelled call logs none. This is the metering foundation for credits.

### Normalization (deliberately forgiving)

- `normalizeList` keeps strings only, trims, drops empties, caps at 8.
- `normalizeSections` accepts an array or a comma/semicolon string. Caps at 8.
- `normalizeActs` accepts a string or an object, reading the name from `act`, `name`, `title` or `statute` and the text from `relevance` or `note`. Caps at 6.
- The client re-checks `Array.isArray` before rendering.

Where to set them:
- `npm run dev` reads **`.env`**.

## Roadmap and decisions

Decided, in build order:

1. Done: Cloudflare adapter, D1, Wrangler config.
2. Done: token usage logging.
3. Done: anonymous daily quota (5 per day, no tier features).
4. Done (tested with the emulator and with a real Google account): **Firebase Auth** with Google sign-in. Workers cannot run the Firebase Admin SDK, so the server verifies ID tokens itself (JWT, Web Crypto).
5. Next: **Tiers** for signed-in users, differing by depth of analysis: **Investigative** (current output) and **Research** (deeper: larger output cap, more items, possibly a stronger model). Anonymous users get neither.
6. **Credits and payments.** Credits cost the user more than the token cost to the app (margin), metered from `llm_usage`. Sell "analyses", not raw tokens. Stripe or Razorpay, undecided. Ledger in D1, atomic and idempotent, with refunds on failure.

Hosting history: Vercel was considered and dropped. Cloudflare allows commercial use on its free plan, and it covers rate limiting, a store and (later) a bot challenge in one account. Vercel Hobby is non-commercial.

Cost safeguards: set a hard monthly spend cap in the model provider's billing settings before any public deploy. Per-IP and per-cookie limits do not stop a determined multi-device user.

## Known issues and open work

000000. **The browser route was run live on 8 Nov 2026** (Chrome, real OpenAI, real Indian Kanoon and `api.sci.gov.in`): verify, research and compare all completed through relay, browser extraction and write steps; a 28-page Supreme Court PDF became 63 paragraphs in 0.5 s in the browser (same as Node); the relay's SHA-256 matched an independent hash; a grant was refused for an address it did not name, for another visitor, and on replay; PDF-sourced support was confirmed and the independent PDF attestation ran and agreed (about 37k tokens). Limits: (1) **the free-plan CPU claim is unmeasured inside workerd** (timers freeze there); the Worker now only relays bytes, hashes them (1 to 2 ms for 0.6 to 3 MB in Node), verifies HMACs, parses the excerpts the browser sends (up to 300k characters of JSON) and runs `quoteSupported`/`closestPassage` over at most 60k characters per source, which should fit but needs a real deploy to confirm; (2) **the text is the browser's**: a user could edit it to fake a "verified" report (they would only fool themselves; the label says so, PDF quotes are re-checked by a model, and the stamp records which file was fetched but cannot prove the text is faithful); (3) the quota unit is taken in step 1, so a user who closes the tab between the steps loses it; (4) `/api/fetch` is bounded to a grant's addresses and 15 minutes but one grant can be fetched from repeatedly in that time; (5) the browser reads every page serially, so a run with several large judgments or PDFs can take a minute on a slow device; (6) a PDF's title is derived from its file name or host, and a PDF that is only scanned images has no text and is skipped; (7) the independent PDF check is a model's reading, a second opinion not a proof, and the PDF must be fetchable by the provider; (8) compare's identify step still cannot confirm a case that exists only as a PDF (it cannot parse one), though verify can.
00000. **Verify cites was run live on 8 Nov 2026** (4 mixed citations, `gpt-4.1` search, `gpt-5.1` support check): 15 to 19 s, about 10 cents (unverified list prices). Across three runs the real cases were found every time and the cited-for-the-wrong-point case was flagged every time; the made-up case was reported not found twice and once matched a different real case with the same party names (now reported as a possible different case). Weaknesses: a search can miss a real case (the report says "does not prove the case does not exist"); a real case whose page does not print its reference shows a warning rather than a tick; only Indian Kanoon pages are read; a long judgment is read in excerpts, so "point not found in the passages read" is not proof the judgment does not say it; one run is a sample.
0000. **Compare cases was run live once (8 Nov 2026), with `gpt-4.1` search and a `gpt-5.1` writer.** Identify took 5 s, the comparison 54 s, about 22 cents at list prices as remembered (unverified). 39 of 43 lines confirmed, 5 dropped. Weaknesses: only Indian Kanoon pages can be compared, so a case that exists only as an official PDF cannot be; the search for overturning decisions finds mostly decisions that applied the cases rather than overruled them (the section is labelled by effect: Overruled / Reversed / Doubted / Followed / Applied); case headings are the writer's own and unverified; one run is a sample.

## Conventions for contributors and agents

- Match the existing style: tabs, single quotes, Svelte 5 runes, Tailwind utilities in markup.
- Import shared code through `#lib/...js`.
- Keep model-output normalization forgiving. Do not make the endpoint fail on a slightly wrong shape.
- Keep the "not legal advice, verify against primary sources" disclaimers.
- Never truncate or rewrite the user's input.
- Never commit secrets, `.env`, `.dev.vars`, service-account files or `design/`. Firebase web config is public by design; a service-account JSON is not.
- No raw colors (hex, `rgb()`, and so on) outside `src/routes/layout.css`. Use the token classes (`bg-surface-1`, `text-text-primary`, `border-border-subtle`). `npm run check:tokens` enforces it.
- **Never start a second dev server in the same checkout with different env vars** (for example a mock provider through `OPENAI_BASE_URL=... npm run dev`). `.svelte-kit/generated/dev/env/config.js` is shared and is rewritten with the values the last server started with, so a developer's running dev server silently starts calling the mock (and fails with `ECONNREFUSED`). Test against a mock in a separate copy of the project (rsync it without `node_modules`, `.env` and `.svelte-kit`, symlink `node_modules`). To repair it, start `npm run dev` once with no overrides, or restart the dev server.
- Run `npm run check` and `npm run check:tokens` before committing. For UI changes, look at the page in a browser. `curl` tests do not catch missing markup.
